# 部署、备份与恢复

本地完整应用仍从 `start.ps1` 或 `backend/run.py` 启动。Python最低3.12，Node最低22.12；依赖按仓库两个锁文件安装。默认只监听127.0.0.1，模型Key继续由用户后续填写。

## 自动备份

默认 `BACKUP_ENABLED=true`、`BACKUP_INTERVAL_HOURS=24`。SQLite备份放在数据库同级 `.backups/`，密钥是同级 `.runtime/backup.key`；MySQL默认使用backend目录下这两个位置，也可通过 `BACKUP_DIR`、`BACKUP_KEY_FILE` 改到专用持久目录。服务健康检查 `/health` 返回最近备份状态和时间，不返回磁盘路径或密钥。

备份包含24表一致快照、资料原文件及实际会话密钥；使用AES-256-GCM认证加密，密钥单独保存，不能丢失。备份不包含 `.env` 中的模型Key、数据库连接密码等部署配置，请由部署者另行安全保管。没有自动清理旧备份，应由部署者按磁盘容量制定保留策略。

备份时SQLite短暂阻止写入；MySQL在REPEATABLE READ事务中锁住账号后读取一致快照。运行一个应用进程，避免多个进程互相恢复任务或同时调度备份。停机期间无法执行任务，重新启动后补做；长期离线机器需要操作系统定时启动服务。

停止应用后也可手动备份（在backend目录）：

```powershell
.venv/Scripts/python.exe -X utf8 tools/backup.py create
.venv/Scripts/python.exe -X utf8 tools/backup.py restore 路径/备份.enc 路径/全新恢复目录 --key 路径/backup.key
```

恢复目录必须不存在，程序不会覆盖当前库。恢复完成后包含 `fmzh.db`、`uploads/` 和 `.runtime/session.key`；程序将资料路径指向新目录。先设置进程环境 `DATABASE_URL=sqlite:///恢复目录/fmzh.db`、`UPLOAD_DIR=恢复目录/uploads` 启动隔离实例，再检查登录、资料预览、任务和统计。确认结果后由部署者在停写窗口切换，原数据保留作回退。

## Linux / MySQL

使用 `mysql+pymysql://用户:密码@主机:端口/库名?charset=utf8mb4`，提前建立空库，字符集utf8mb4、推荐二进制排序 `utf8mb4_bin`，账号只授权本应用数据库。通过进程环境设置独立的 `SECRET_KEY`（至少32个随机字符）和上传、备份持久目录，勿把密码写入Git或命令行日志。

Windows→Linux移动上传文件后，数据库内资料绝对路径也必须对应迁移后的目录；可先用加密备份恢复工具建立新目录，再将恢复后的SQLite库迁移至MySQL。停止源库写入并确认目标空库后，在环境变量中设置 `FMZH_SOURCE_DATABASE_URL`、`FMZH_TARGET_DATABASE_URL`，运行 `python tools/migrate_database.py`。工具逐表核对主键顺序下的数据摘要，任一不一致回滚整个插入事务；源库只读，不自动覆盖目标数据。启动前再次核对上传路径、容量和外键。

MySQL建表采用LONGTEXT（超过64KB的正文/JSON）、微秒DATETIME、DOUBLE，避免文本截断和精度变化。业务自然日显式取北京时间；为兼容既有库中的无时区打卡/锁定时间，Linux进程还应设置`TZ=Asia/Shanghai`。实测环境是Ubuntu、Python3.12与MySQL8.0.46；其他版本需重新验证。

## 公网运行条件

公网主机需由部署者提供域名、TLS证书、持久磁盘和数据库。使用 `deploy/Caddyfile.example` 终止HTTPS，后端仍绑定本机8000；只放通80/443，不公开MySQL和后端监听。证书、域名和主机未提供，因此当前没有公网部署验收结论。

运行中的数据库、上传、会话与备份密钥应放在已启用BitLocker（Windows）或LUKS（Linux）的持久卷，并以独立系统账号和最小目录权限运行。生产上线前实际检查卷加密状态和重启挂载、权限、HTTPS、证书续期、备份及隔离恢复。应用不会擅自启用或重配用户主机磁盘加密；AES加密备份仅覆盖备份文件，不覆盖工作目录。
