## 2. 公式速查（被问到就背这些）

### 2.1 期末压力指数（0~100）

```
压力指数 = 30×考试密集度 + 30×任务积压率 + 20×(1−任务完成率) + 20×考试临近度
```

- 考试密集度 = min(1, 未来 7 天考试场次÷4)
- 任务积压率 = 逾期未完成任务数÷总任务数
- 任务完成率 = 已完成任务数÷总任务数
- 考试临近度 = min(1, 21÷最近一场考试剩余天数)
- 分档：**<40 轻松 / 40~60 适中 / 60~80 偏压 / ≥80 高压**（≥60 首页提示并建议开启救急模式）
- **边界约定**：无考试 → 密集度、临近度取 0；考试当天（剩余 0 天）→ 临近度取 1；无任务 → 积压率、完成率取 0

### 2.2 情绪综合评分（0~5）

```
情绪综合评分 = 0.4×情绪项 + 0.3×完成项 + 0.2×压力项 + 0.1×达标项
```

| 分项 | 公式 | 说明 |
|---|---|---|
| 情绪项 | 5×(情绪自评−1)÷4 | 自评 1~5 |
| 完成项 | 5×当日任务完成率 | |
| 压力项 | 5−压力指数÷20 | |
| 达标项 | 5×连续达标因子 | 连续达标因子 = min(连续达标天数,7)÷7，连续达标天数 = 连续「当日任务全部完成」的天数 |

> 答辩点：**四个分项都归一化到 0~5 再加权，总分数学上精确落在 0~5**，不会出现“满分 5 分实际最高 3.4”的口径漏洞。

> **低分处理（综合评分低于 2.5）**：系统在节奏建议之外提供「减轻当日任务 / 暂停半天」选项；学生选择后，在考试日期、每日可用时间、任务优先级约束下重排未完成任务，剩余时间不足时明确提示取舍、不自动增加后续负担；所有调整经学生确认后生效（用例 7.7）。

### 2.3 两级权重 + 分数区间目标

- **资料权重**（资料可不可信）：`老师标注重点 ＞ 历年试题/练习题 ＞ 平时作业/课堂笔记 ＞ 教材章节/PPT/实验报告`
- **知识点权重**（知识点重不重要）：历年题必考点 → 基础值，再按用户画像（目标/薄弱章节）调整
- **备考目标区间**：川大本科原有 10 档分数、绩点和滑条规则不变。目标仅影响复习内容与时间侧重：同一预算内分配基础巩固、常见题与错题、综合与限时训练，结合基础/薄弱章节和剩余天数调整；展示精确分钟和超额未安排提示。真实后端保存结果，反馈重排同步分钟；这些比例不是试卷分值或题型频率。

## 3. 问答要点（老师/同学预判）

**Q：为什么用大模型，不用写死规则？**
A：系统的输入是「多来源、非结构化的复习资料 + 学生自然语言描述」，规则写死无法覆盖。我们不是放任大模型自由发挥——三层控制：① 自然语言先转**固定 JSON 画像**；② **固定提示词**约束角色与范围；③ 输出**固定 JSON Schema**，解析失败有兜底重试，且默认 Mock 模式保证演示永远可用。

**Q：大模型会胡说八道，复习建议错了谁负责？**
A：第一，回答范围限定在“基于用户上传资料 + 课程资料 + 考试目标”（USR-0048）；第二，页面明示“AI 生成内容仅供复习参考”（USR-0049）；第三，每个结论带**推荐依据**（来自历年高频题/老师重点/用户薄弱项），用户可自行判断。

**Q：压力指数、权重这些公式哪来的？**
A：团队自定义的**可解释加权模型**：来源层级给资料权重、历年题频次定知识点基础权重、画像做个性化调整；压力指数四个分项各有明确定义和边界约定（无考试/无任务/考试当天都有规定），不是拍脑袋。

**Q：跟超级课程表、滴答清单这类 App 有什么不同？**
A：它们做通用日程；我们**只做期末冲刺这一个场景**：多源资料整合分析（不是单文件总结）、按目标和基础差异化推荐（不是所有人同一套计划）、压力指数/救急模式/今日三件事这些人性化功能直面期末焦虑。

**Q：为什么用 SQLite 不直接用 MySQL？**
A：需求文档口径：开发与演示阶段以 SQLite 实现等价替代，切换只需改 `DATABASE_URL` 连接配置一行，SQLAlchemy 模型不用动。

**Q：安全性怎么保证？**
A：JWT 会话（7 天）+ bcrypt 密码哈希；业务查询按用户隔离；连续 3 次密码错误锁定账号；重要删除有确认，关键操作日志已落库并由管理员分页查看，确认覆盖的剩余差距见 README。

**Q：哪些功能还没做完？**
A：MVP 主线（注册登录→录考试→传资料→AI 分析→任务打卡→统计）已全流程打通。**当前已完成、基础版与待开发项目以 README 第 2 节为准**，演示前核对最新状态；详细验收差距统一查本地工作日志，不在本页重复维护功能进度清单。

**Q：隐藏需求是什么？**
A：原始需求列表没提、但系统必要的内容（如数据隔离、操作日志），需求分析 2.4 节已补充并纳入对照表。

**Q：这个项目后续怎么做？**
A：当前行动顺序统一查本地 `PROJECT_HANDOFF.md` 第 3 节，负责人范围见 README 第 8 节；采用分支开发、PR 审查与真实数据验收。

## 5. 两个 Mock 开关（现场出故障时救命）

| 开关 | 位置 | 当前 | 作用 |
|---|---|---|---|
| `VITE_USE_MOCK` | `frontend/.env.local` | 默认 **true**（预览态） | true = 使用演示数据；联调真实后端设 false 并重启 Vite，无需改源代码 |
| `LLM_MOCK` | `backend/.env` | **true** | true = 大模型返回内置示例，**不需要网络和 Key**，全流程可演示 |

**故障预案**：AI 分析报错 → 确认 `LLM_MOCK=true`；首页数据对不上 → 检查 `VITE_USE_MOCK=false` 且后端已启动；大模型没配 Key → 保持 Mock 即可，口径“接入真实大模型 API 只改配置”。
